# Own the kitchen, rent the line cooks

Kitchen should not be built on top of the Codex harness, and it should not be a from-scratch agent harness either. The October 2026 evidence points to a third path. Kitchen should own a thin Bun/TypeScript orchestration daemon, which holds the event log, worktrees, the Kitchen Manager and the attention queue. It should drive existing harnesses as interchangeable **workers** through their server protocols: the Codex app-server, `opencode serve`, pi RPC, the Claude Agent SDK, and ACP for the long tail. It should use **pi-ai/pi-agent-core** (or the Vercel AI SDK) as the paved-road library for the Kitchen Manager and for a first-party "any model" worker. Codex is the best single-provider engine available, with a Rust core, OS sandboxing, a JSON-RPC app-server with approvals as server requests, and managed worktrees. It is also locked to the OpenAI Responses API, ships several alpha builds a day, and already has its own single-provider multi-agent mode that overlaps kitchen's. The strongest prior art is architectural rather than a base to fork. opencode independently built kitchen's exact persistence design: SQLite with an append-only `event` table keyed by `(aggregate_id, seq)` and replay-after-seq over SSE. Claude Code Agent View shipped kitchen's attention UX for Claude only. Meanwhile the "dashboard of parallel worktree agents" has been commoditized by a dozen tools. Kitchen's defensible core is a conversational manager agent over **heterogeneous** workers, backed by a durable, replayable, cross-harness event log exposed as an API. No surveyed open-source project or first-party product ships that combination.

## Three layers, not one: how the 2026 landscape actually divides

The landscape is easiest to read as three stacked layers, and kitchen's design question changes depending on which one is in view. The bottom layer is **paved-road libraries**: provider abstraction plus a minimal tool loop, such as pi-ai/pi-agent-core, Vercel AI SDK 7, Mastra, LangGraph.js and the OpenAI Agents SDK. The middle layer is **full coding harnesses** that bundle tools, sandboxing, compaction and sessions: Codex CLI, opencode, pi-coding-agent, Gemini CLI, Goose, Cline, Qwen Code, OpenHands, Crush and Aider. The top layer is **orchestrators** that run many harness sessions in parallel: Claude Code Agent View, the Codex app, Conductor, vibe-kanban, Orca, Emdash, Agent Orchestrator and claude-squad. Kitchen belongs in the top layer. Its April spec already treated workers as a pluggable interface beneath the Kitchen Manager, which makes "build on Codex" a category error, because Codex sits one layer down.

The middle layer has converged on a common shape. Every serious harness now exposes a machine protocol, not just a TUI. Codex has a JSON-RPC app-server over stdio, unix socket or websocket ([Codex docs: App Server](https://learn.chatgpt.com/docs/app-server)). opencode has an HTTP server with an OpenAPI 3.1 spec and SSE events ([opencode docs](https://opencode.ai/docs/server/)). pi has JSONL RPC over stdio plus an in-process SDK ([pi rpc.md](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/rpc.md)). Qwen Code has an experimental `qwen serve` HTTP+SSE daemon ([Qwen Code](https://github.com/QwenLM/qwen-code)). The Agent Client Protocol has become the lingua franca: about 38 native agents are listed, including Gemini CLI, Goose, Cline, OpenCode, OpenHands, Qwen Code, Copilot and Cursor, and Codex and pi work through adapters ([ACP agents](https://agentclientprotocol.com/overview/agents)). That convergence is the single most important fact for kitchen. It means kitchen's spec §6 `Worker` interface can be implemented as thin protocol adapters rather than by owning a loop.

## Codex is a superb worker engine and the wrong foundation

The case for building on Codex is real. The app-server speaks JSON-RPC over stdio, a unix socket or websocket and is organized around Thread, Turn and Item. Approvals arrive as server-to-client requests (`item/commandExecution/requestApproval`, `item/fileChange/requestApproval`, `item/tool/requestUserInput`). `codex app-server generate-ts` emits TypeScript types for the installed version ([Codex docs: App Server](https://learn.chatgpt.com/docs/app-server)). That maps almost one-to-one onto kitchen's `awaiting_input` state and "what needs me" queue. The sandbox stack would take months to replicate. Linux now uses bubblewrap, macOS uses Seatbelt, Windows has a dedicated sandbox service, and an AI "Guardian" auto-reviewer is Stable ([linux-sandbox README](https://github.com/openai/codex/blob/main/codex-rs/linux-sandbox/README.md); [features](https://github.com/openai/codex/blob/main/codex-rs/features/src/lib.rs)). One app-server process hosts many threads, and `thread/start` takes a per-thread `cwd`, `sandbox`, `approvalPolicy` and `modelProvider` ([v2/thread.rs](https://github.com/openai/codex/blob/main/codex-rs/app-server-protocol/src/protocol/v2/thread.rs)). Codex also has the cleanest subscription story in the market. An OpenAI executive said in July 2026 that ChatGPT accounts work in third-party harnesses, and that Pi and OpenCode already account for about 10% of Codex traffic ([manifest.build](https://manifest.build/blog/chatgpt-plus-tokens-third-party-harnesses/)).

Three facts disqualify it as kitchen's base. First, **Codex speaks only the OpenAI Responses API**. `wire_api = "chat"` became a hard error on February 1, 2026, and the only built-in providers are OpenAI, Bedrock, Ollama and LM Studio ([model-provider-info](https://github.com/openai/codex/blob/main/codex-rs/model-provider-info/src/lib.rs); [discussion #7782](https://github.com/openai/codex/discussions/7782)). Claude or Gemini workers inside Codex need a translating gateway such as Bifrost or LiteLLM. They also inherit a GPT-tuned prompt and Codex's own `apply_patch` grammar, and practitioners report that weaker models "often fail to properly serialize tool outputs, causing loop crashes" ([heyuan110](https://www.heyuan110.com/posts/ai/2026-09-15-configuring-third-party-models-in-codex/)). For a harness whose first design goal is "Claude and Codex both first-class", that is a structural mismatch, not a configuration detail. Second, **churn is extreme**. Nine `0.162.0-alpha` tags appeared in about 32 hours on October 2–3, the workspace carries placeholder `0.0.0` versions, and the protocol has no semver promise beyond a per-field `experimentalApi` gate ([releases](https://github.com/openai/codex/releases); [experimental_api.rs](https://github.com/openai/codex/blob/main/codex-rs/app-server-protocol/src/protocol/experimental_api.rs)). Forking 118 Rust crates at that cadence is a full-time job, and Rust also breaks kitchen's Bun/TS single-language stack. Third, **Codex already ships the single-provider version of kitchen's idea**. Its Stable multi-agent tools (`spawn_agent`, `send_input`, `wait_agent`) default to six threads at depth one, and children copy the parent's provider (`config.model_provider = turn.provider.info().clone()`). Its managed `worktree` crate and "agent command center" overlap kitchen's workspace and attention features ([child_config.rs](https://github.com/openai/codex/blob/main/codex-rs/core/src/agent/child_config.rs); [worktree crate](https://github.com/openai/codex/blob/main/codex-rs/worktree/src/lib.rs)). Building on Codex means building a reskin of something OpenAI will keep improving, while giving up the one axis it will never cover.

The April spec needs one concrete correction here. §11.2 plans a `CodexWorker` on `@openai/codex-sdk`, but that SDK wraps `codex exec --experimental-json` and spawns one CLI process per run ([sdk/typescript](https://github.com/openai/codex/blob/main/sdk/typescript/src/exec.ts)). The exec path is non-interactive, so approval round-trips never reach kitchen. That would make `awaiting_input`, the heart of "what needs me", impossible for Codex workers. The Codex adapter should drive `codex app-server` directly, using a pinned binary and generated types. It should use `ephemeral` threads or treat Codex's rollout JSONL as a secondary transcript to avoid two sources of truth. It should use experimental `dynamicTools` to inject kitchen callbacks such as `report_status` and `ask_manager`. Codex's internal `multi_agent` should be capped so workers don't nest their own orchestration. One open question remains unverified: whether `thread/start.multiAgentMode` can fully disable subagent tools from an external client.

## opencode and pi already built half of kitchen's backend

The strongest prior art for kitchen's *daemon* comes from opencode, not Codex. Since late January 2026 opencode has stored state in SQLite through Drizzle. It has an `event_sequence(aggregate_id, seq, owner_id)` table and an `event(id, aggregate_id, seq, type, data)` table with a unique index on `(aggregate_id, seq)` ([core/src/event/sql.ts](https://github.com/anomalyco/opencode/blob/dev/packages/core/src/event/sql.ts)). Events are defined with versioned schemas, emitted before mutation and applied by projectors ([sync README](https://github.com/anomalyco/opencode/blob/dev/packages/opencode/src/sync/README.md)). Its `sessions.events({sessionID, after})` endpoint "replays durable events after the optional aggregate sequence, continues with newly committed durable events, excludes live-only fragments". The separate instance-wide stream gives "no replay guarantee", and neither stream auto-reconnects ([CONTEXT.md](https://github.com/anomalyco/opencode/blob/dev/CONTEXT.md)). That is kitchen spec §7–8 almost line for line: durable vs live-only events, and `sinceSeq` subscription with the client owning resume. It validates kitchen's design and is MIT code kitchen can copy with attribution. opencode also offers kitchen a mature worker. Over HTTP it exposes sessions, prompt, interrupt, fork, revert, diff, a durable event stream and permission/question reply endpoints. Its worktree service runs `git worktree add --no-checkout -b` with a start-command hook ([worktree/index.ts](https://github.com/anomalyco/opencode/blob/dev/packages/opencode/src/worktree/index.ts)). Since v1.18.34 it sends namespaced session and parent-session identity headers, which helps attribute cost per worker ([releases](https://github.com/anomalyco/opencode/releases)).

opencode is a poor *base* for the same reasons it is a good reference. It is mid-migration across four seams at once: legacy `/session` to `/api`, `@opencode-ai/sdk` to `sdk-next`, the AI SDK to a native `@opencode-ai/llm`, and Bus events to SyncEvent. Its internals are pervasively Effect-TS, and its background jobs are process-local: "process restart clears the registry" ([CONTEXT.md](https://github.com/anomalyco/opencode/blob/dev/CONTEXT.md)). It has no OS sandbox, and its default permission is `"*": "allow"` ([agent.ts](https://github.com/anomalyco/opencode/blob/dev/packages/opencode/src/agent/agent.ts)). It has a history of severe server bugs, including CVE-2026-22812 (CVSS 8.8, unauthenticated shell exec) and CVE-2026-22813 (CVSS 9.4, XSS to RCE) ([lilting.ch](https://lilting.ch/en/articles/opencode-cve-2026-22812-22813-rce)). Its experimental workspace/control-plane layer, with local and remote targets and move-session, also points toward kitchen's territory. That is a competitive signal as much as a churn signal.

pi supplies the paved road. **pi-ai** covers about 35 providers plus any OpenAI-compatible endpoint, with typed streaming events, partial-JSON tool-call streaming and a unified reasoning knob. It handles cross-provider handoff by converting foreign thinking blocks to `<thinking>` text. Its OAuth refresh runs "under a credential-store lock, so concurrent requests and processes cannot double-refresh", and it ships a faux provider for tests ([pi-ai README](https://github.com/earendil-works/pi/blob/main/packages/ai/README.md)). **pi-agent-core** adds a small `Agent` class. It has events (`turn_start`, `message_update`, `tool_execution_*`), per-tool parallel or sequential execution, before/after tool hooks, and `steer()` and `followUp()` queues. Persistence is deliberately left to the host ([agent-core README](https://github.com/earendil-works/pi/blob/main/packages/agent/README.md)). That is the right shape for a daemon that owns its own log. OpenClaw embeds pi in production through `createAgentSession()` and adds auth-profile rotation and per-channel prompts ([OpenClaw docs](https://docs.openclaw.ai/pi)). Mario Zechner's design thesis also gives the first-party worker an evidence-backed minimum: four tools, a system prompt under 1,000 tokens, exact-match edits, and Terminal-Bench 2.0 results competitive with heavier harnesses ([Zechner](https://mariozechner.at/posts/2025-11-30-pi-coding-agent/)).

The cautions on pi are governance and velocity rather than quality. Earendil acquired pi in April 2026 ([Earendil](https://earendil.com/posts/announcement-reflection/)). The npm scope moved from `@mariozechner/*` to `@earendil-works/*`, 1.0.0 landed only on October 1, and outside PRs are auto-closed by default ([CONTRIBUTING](https://github.com/earendil-works/pi/blob/main/CONTRIBUTING.md)). Earendil's RFC 0015 promises the core stays MIT but plans Fair Source and proprietary products alongside it ([RFC 0015](https://rfc.earendil.com/0015/)). Its experimental **pi-durable** runtime overlaps kitchen directly. It offers atomic commits, crash resume, owned child conversations, background tasks that survive parent abort, a `taskGraph()` "for a task panel", and SQLite storage. Its watch semantics are snapshot-plus-live ("nothing is replayed"), however, which differs from kitchen's seq replay ([pi-durable README](https://github.com/earendil-works/pi/blob/main/packages/durable/README.md)). Vercel AI SDK 7 is the credible alternative paved road. It offers `ToolLoopAgent` with typed approval policies, a durable `WorkflowAgent`, a sandbox abstraction, `@ai-sdk/tui`, and an experimental `HarnessAgent` that wraps Claude Code, Codex and Pi behind one interface ([Vercel changelog](https://vercel.com/changelog/ai-sdk-7); [AI SDK harnesses](https://ai-sdk.dev/docs/ai-sdk-harnesses)). It is broader and more corporate-stable than pi-ai. It is less specialized for coding-agent context handoff, and its harness wrapper is explicitly "Expect breaking changes".

## The dashboard is commoditized; the manager agent is not

The orchestration layer has filled in fast since kitchen was shelved. Claude Code Agent View launched May 11, 2026. It is one screen of background sessions sorted into needs-input, working and done, with inline replies and PR markers ([Anthropic](https://claude.com/blog/agent-view-in-claude-code)). By late June, workers stopped by a daemon restart resumed automatically ([Classmethod](https://dev.classmethod.jp/en/articles/20260630-cc-updates-v2-1-196/)). Claude Code's experimental agent teams add a lead with a shared task list and mailbox. Their limits matter to kitchen: they are Claude-only, one team per session, unable to restore in-process teammates on `/resume`, not worktree-isolated by default, and unable to spawn in Agent SDK sessions ([agent teams docs](https://code.claude.com/docs/en/agent-teams)). In open source, Orca (MIT, about 84k stars, created March 2026) runs any of 40+ CLI agents in per-agent worktrees with "unread state" for when an agent "finishes or needs attention" ([Orca](https://github.com/stablyai/orca)). vibe-kanban, Emdash, Agent Orchestrator, Bernstein and claude-squad all do worktree-per-agent across many harnesses, and in every case the human is the dispatcher ([Augment survey](https://www.augmentcode.com/tools/open-source-agent-orchestrators)). The company behind vibe-kanban shut down in April 2026 ([VirtusLab](https://virtuslab.com/blog/ai/vibe-kanban/)). That is a reminder that this layer is being squeezed by first-party products: Agent View, the Codex app, GitHub Mission Control ([GitHub](https://github.blog/news-insights/product-news/welcome-home-agents/)) and Antigravity's manager view.

Two things remain rare. One is a **conversational manager agent** that turns a conversation into jobs, picks a provider per job, and triages workers into a ranked queue. A handful of small projects such as Vigil and Paseo are reaching for this, though those findings are snippet-level and unverified ([awesome-agent-orchestrators](https://github.com/andyrewlee/awesome-agent-orchestrators)). The other is a **durable, replayable, cross-harness event log exposed as an API** that other clients can subscribe to. Agent View has neither an external API nor a non-Claude worker, and Orca wraps terminals rather than protocols. That gap is kitchen's reason to exist, and it argues for keeping the orchestrator thin and owned. Because the dashboard is a commodity, kitchen should spend its effort on the Kitchen Manager's triage quality and the event log's fidelity, not on UI breadth. The honest steelman against building at all is that Agent View already solves steven's original pain for Claude-only work. Kitchen is worth reviving only if cross-provider dispatch, meaning Codex-on-ChatGPT-plan alongside Claude alongside open-weight models, is a real daily need.

## Recommended architecture: an ACP-shaped supervisor with four adapters

The recommendation is to **roll your own orchestrator on a paved road, and treat every harness, Codex included, as a rented worker**. Concretely, kitchen keeps its spec's Bun daemon, HTTP+WS API, SQLite WAL event log with `sinceSeq` replay, worktree "departments" and TUI. Its §6 `Worker` interface is redefined with ACP semantics, because ACP already standardizes `session/new`, `session/load`, `session/prompt`, `session/cancel`, `session/update` and `session/request_permission` ([ACP protocol](https://agentclientprotocol.com/protocol/overview)). Kitchen-specific needs that ACP does not standardize ride on `_kitchen/*` methods and `_meta`: worktree binding, model selection, cost, and structured done/blocked outcomes. Behind that interface sit four first-class adapters. **CodexAppServerWorker** speaks app-server JSON-RPC to a pinned `codex` binary, one process per worker for crash isolation, with `cwd` set to the worktree, `sandbox: workspace-write`, approvals mapped to `input.requested`, and ChatGPT login through `account/login`. **ClaudeAgentWorker** runs on the Claude Agent SDK with an API key, keeping the spec's §11.1. **OpencodeWorker** runs `opencode serve` per worktree on a random port with `OPENCODE_SERVER_PASSWORD`, subscribes to `/api/session/{id}/event?after=seq`, and persists opencode's seq cursor in kitchen's log. **KitchenNativeWorker** is a pi-agent-core loop over pi-ai with read/write/exact-match edit/bash, `apply_patch` offered for OpenAI models, and cwd pinned to the worktree. It handles "any model" jobs and doubles as the reference implementation. A generic **AcpWorker** then covers Gemini CLI, Goose, Cline and Qwen Code with no bespoke code. The Kitchen Manager itself becomes a pi-agent-core `Agent` (or AI SDK `ToolLoopAgent`) inside the daemon rather than a Claude Code worker. Its tools are the spec's MCP set plus `dispatch_worker`, `steer_worker` (backed by `steer()`/`turn/steer`) and `raise_attention`. That frees the KM from Claude subscription constraints and lets it run on any model.

The key risks are concrete and mostly manageable. **Subscription-auth terms** are the sharpest. Anthropic blocked third-party OAuth on January 9, 2026, wrote the prohibition into its docs on February 19, and enforced it against third-party harnesses on April 4 ([VentureBeat](https://venturebeat.com/ai/anthropic-cracks-down-on-unauthorized-claude-usage-by-third-party-harnesses/); [Gigazine](https://gigazine.net/gsc_news/en/20260220-anthropic-third-party-block)). Yet pi 1.0.0 still added an "Anthropic copy code login" ([pi CHANGELOG](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/CHANGELOG.md)). Kitchen must route Claude through API keys and the Claude Agent SDK, whose TypeScript package is governed by Anthropic Commercial Terms rather than MIT ([Claude Agent SDK docs](https://platform.claude.com/docs/en/agent-sdk/overview)). It should disable pi-ai's Anthropic OAuth path outright. OpenAI's tolerance for ChatGPT-plan use is informal, resting on executive statements with no written policy ([Simon Willison](https://simonwillison.net/2026/Mar/7/codex-for-open-source/)). Driving the official `codex` binary is therefore the lowest-risk way to use it. **API churn** is universal: Codex alphas several times a day, opencode's dual APIs, pi's renames and scope move, and AI SDK harnesses marked experimental. The mitigation is to pin exact versions, regenerate Codex types on each bump, talk only over process protocols (never in-process internals such as opencode's sdk-next), and keep a contract test per adapter. **Bun compatibility** is unverified across the board. pi targets Node ≥22.19 with only Bun install smoke tests, AI SDK 7 officially states Node 22+, and the Claude Agent SDK spawns a CLI subprocess. Kitchen should spike pi-ai, pi-agent-core and the Claude Agent SDK under `bun build --compile` in week one, and keep Node as a fallback runtime for the daemon. **Isolation** falls to kitchen for every worker except Codex, because opencode and pi ship no OS sandbox. Worktrees protect git state, not the host. **Dual transcripts**, kitchen's log plus each harness's own JSONL or SQLite, will drift unless kitchen records the harness session id and cursor as metadata and treats the harness store as authoritative for resume. Finally, there is **platform absorption**. Codex's command center, opencode's control plane and pi-durable are each converging on parts of kitchen, so the adapter boundary is also an exit hatch. If one of them becomes the better supervisor, kitchen can demote its own layer without rewriting workers.

## Conclusion

The question "build on Codex or roll your own?" turns out to be miscast. In 2026 the harness layer has become a set of servable engines with converging protocols. The decision that matters is which layer kitchen owns, and the answer is the one nobody else ships: a provider-neutral manager agent over a replayable cross-harness log. The most useful prior art is a schema, not a codebase. opencode's `(aggregate_id, seq)` event table and explicit replay semantics are effectively a field test of kitchen's spec, so kitchen can adopt that persistence layer with high confidence and spend its novelty budget on attention ranking.

The revived spec should make three concrete changes. It should replace `@openai/codex-sdk` with the Codex app-server, because the exec-based SDK cannot surface approvals. It should make the Kitchen Manager an in-daemon pi-agent-core or AI SDK agent rather than a Claude Code worker, so the KM is not tied to one vendor's terms. And it should adopt ACP semantics for the worker interface, so that every future harness arrives as configuration rather than code. The remaining uncertainties should be settled by a one-week spike before any further design work: Bun behavior of the TS libraries, whether Codex subagents can be fully disabled per thread, and per-instance memory cost of running N `opencode serve` processes.
